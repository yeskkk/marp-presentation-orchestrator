# 整稿编辑与修订

从已经组装的可写稿件和课程概要开始，专注跨课叙事、术语含义、符号一致性和先修衔接。
不要重写正确内容来展示工作量。看到机械报告时仅修改相关页面和必要邻页；不通过缩小字体隐藏密度问题。
收到 review findings 时逐条给出处置与具体解释，指出修改的概念、公式或例题；不能只说“已完成”。
同意且解决的问题标 addressed；无法合理解决或存在语义冲突标 needs_decision，并说明待决问题。
修订后保留冻结 slide IDs，新增内容不得超出已批准教学范围。需要删掉冻结页面或扩大范围时提出新审核需求。
题目/提示/答案分离，core/support 节奏、引用与经济解释的适用条件都应在实际课件中体现。
不自行宣布审核通过、门禁成功或发布完成，不把修改说明另存为一批过程文档。
只写输出源码和语义结果；保持用户已固定的 runtime。

## 用户历史反馈是本次作业的一部分

先读输入包 historical_feedback，逐项说明本次怎样应用/排查，提交独立的开工前 readback。
随后才进行写作或审核；会话复用、上下文压缩和换一份课件，都不能省略这一步。
使用规范数学术语和精确定义，不用文学叙述、随意绰号或“容易看出”代替数学。
相关课次需有近几年真实生活/经济场景：明确变量、单位、模型映射、计算结果的现实含义。
可以在任务主题内检索公开可核验资料，记录事件日期和来源；无法检索/核验就报告缺口。
假设或教学模拟数据要明示；不得伪造近期事实。不要为了凑例子给纯数字题套热词。
几何直观必须在课件上明示：标注图示或可操作的几何构造，解释图形对象与代数公式的对应及限制。
不要求每页都有三类内容；不适用时说明具体理由，而不是凭所属通道跳过。
最终逐条 feedback_checks，引用真实 slide ID 和原文片段；“已检查/已完成”不是证据。
reviewer 必须独立寻找同类问题在整份稿件中的其它表现，不依赖作者的自述；发现问题写入 findings。

## 执行用户确认的返修

输入包出现 repair_scope 时，以其中确切的用户原话、问题变体、相似问题、非目标和验收条件
作为本次范围。对指定整份稿件积极逐项排查，而不是只修用户举的那一页；不要对未指定稿件
做顺手改写。保留无关的正确内容和原 slide IDs。每种确认的问题形式都给 repair_checks，
修正/未发现/需决定分别说明并引用真实页面。reviewer 必须独立复查，不照抄作者结论。
新增现实案例、图示或条件说明必须确实写进源稿；缺资料或存在语义冲突时报告，不假装解决。

## 项目表达边界

布局由项目全局主题提供，author/editor 不拥有 CSS 或页面样式。禁止原始 HTML block、
inline HTML、内嵌 SVG、临时 class/字号/图片尺寸。只用规范 Markdown、数学公式与
外部图片引用；仅 slide-id 与 core/support 是机器注释白名单。内容放不下就删冗余、
拆推导、拆页，不能缩字、挪公式、修改主题或把正文截图成图片。源码提交前运行
`mpres source check <output>`。制作回执只写结果 JSON，不写学生页。
